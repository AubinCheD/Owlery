# Owlery 0.2 — plan d'implémentation

> **Pour les agents d'exécution :** sous-skill requis : superpowers:subagent-driven-development
> (recommandé) ou superpowers:executing-plans, tâche par tâche. Les étapes sont des cases à cocher
> (`- [ ]`).

**Objectif :** passer du premier jet (GitHub seul) à une boîte de réception multi-forges, avec
notifications, contrat local et outils de tri, sans rien perdre de l'état du premier jet.

**Architecture :** une crate bibliothèque + exécutable. La lecture des forges passe par un trait
`Fetcher` (réel : HTTP et `gh` ; tests : réponses fictives), l'interface par `App` construite avec
ses dépendances (`StartOptions`), ce qui permet des tests d'interface egui_kittest. Le code propre
à Windows (canal nommé, zone de notification, instance unique) est isolé dans `src/win/`.

**Pile :** Rust 2024, eframe/egui 0.37 (glow), ureq 3 (native-tls), keyring 4, serde_json,
windows-sys 0.61, egui_kittest 0.37 (tests).

**Spécification :** `docs/superpowers/specs/2026-10-21-owlery-0.2-design.md`.

## Contraintes globales

- Un commit par tâche, message en français, terminé par les lignes `Co-Authored-By` et
  `Claude-Session` de la session ; identité git du dépôt ; jamais de push.
- Avant chaque commit : `cargo fmt`, `cargo clippy --all-targets -- -D warnings`, `cargo test`.
- Interface en français ; aucun nom réel ; aucun jeton ni organisation réelle ; aucun accès réseau
  en test (transport factice) ; jamais le vrai coffre en test (`MemoryStore`).
- Champs nouveaux de l'état : `#[serde(default)]` ; `state.json` du premier jet toujours lisible
  (test sur un fichier figé `src/testdata/state-0.1.0.json`).
- Rien d'envoyé à Fawkes, rien de lancé, sans clic de l'utilisateur.

## Points de revue (non couverts par ailleurs, à fixer par un test dans la tâche indiquée)

1. Fil de lecture qui panique : l'interface doit sortir de « Lecture… » et le dire (tâche 1).
2. Jeton enregistré pendant une lecture : une nouvelle lecture doit suivre (tâche 1).
3. Deux Owlery sur le même dossier d'état : le second ne doit pas écrire (tâche 8).
4. Réponse JSON d'une forge sans un champ attendu : l'entrée est sautée, pas toute la lecture
   (tâches 3 à 5, un test par forge).
5. Compte en échec : ses entrées en cache restent, celles des autres comptes sont mises à jour
   (tâche 3).
