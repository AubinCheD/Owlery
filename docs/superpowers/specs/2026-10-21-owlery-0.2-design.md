# Owlery 0.2 — design

Date : 21/10/2026. Suite du premier jet (0.1.0). L'utilisateur a demandé : une passe complète du
code, les points 2 à 4 des « Pistes après le premier jet » (`docs/journal.md`), des fonctionnalités
jugées utiles, superpowers et une feuille de route. L'essai contre GitHub réel (point 1) attend.
Les choix de fonctionnalités lui ont été laissés : ceux qui suivent sont **des choix de Claude**, à
relire par l'utilisateur.

## 1. Intention

Owlery doit devenir l'endroit unique où l'on voit ce qui attend une réponse, sur les trois forges,
sans avoir à garder leurs pages web ouvertes. Une entrée doit mener en un clic à l'action :
navigateur, DragonTree, ou une session Claude dans Fawkes. Rien n'est perdu ni lancé sans
l'utilisateur.

## 2. Objectifs

1. **Revue** : corriger les défauts trouvés par la passe complète (la mienne et celle d'un relecteur
   neuf), chacun avec un test qui le fixe.
2. **Comptes** : plusieurs comptes, sur GitHub (y compris GitHub Enterprise), GitLab (gitlab.com ou
   instance) et Azure DevOps (organisations). Le jeton est saisi dans Owlery et rangé dans le coffre
   de Windows ; le dialogue indique les droits minimaux et vérifie le jeton avant de l'enregistrer.
3. **GitLab** et **Azure DevOps** : mêmes types d'entrées que GitHub, testés sur des réponses
   fictives seulement.
4. **Notifications Windows** par type d'entrée, et rappel quand un report arrive à échéance.
5. **Corriger avec Claude** : demande à Fawkes par le contrat local, prête pour le jour où Fawkes
   aura son canal ; repli visible (copier le contexte) tant qu'il ne l'a pas.
6. **Contrat local côté Owlery** : instance unique, canal nommé qui reçoit `afficher`,
   `actualiser` et `etat` (badges pour DragonTree ou la suite).
7. **Toolchain autonome** : `scripts/setup.ps1` comme Menagerie, plus de dépendance à DragonTree.
8. **Fonctionnalités utiles** (choix de Claude) :
   - détail enrichi : vérifications de CI en échec (nom et lien) et trois derniers commentaires ;
   - dépôts locaux trouvés tout seuls dans des dossiers racines (pour DragonTree et Fawkes) ;
   - annuler (Ctrl+Z) les derniers changements d'état ;
   - tout marquer lu (un groupe, ou la vue filtrée) ;
   - ignorer un dépôt, masquer les auteurs robots (`[bot]`) ;
   - filtres, regroupement, taille et position de la fenêtre gardés entre deux lancements ;
   - titre de fenêtre avec le nombre d'entrées en attente ; icône (une chouette dessinée en code) ;
   - palette : *Aller au dépôt…*.
9. **Superpowers et documentation** : `.claude/settings.json` (greffon superpowers, comme Fawkes),
   `docs/superpowers/` (design, plans), `docs/feuille-de-route.md`.

## 3. Non-objectifs

- Écrire sur les forges (approuver, fusionner, commenter) : toujours dans le navigateur.
- Synchroniser l'état lu / non lu avec les forges, l'API de notifications de GitHub, la vue équipe.
- Lire le coffre de DragonTree (décision du premier jet, inchangée).
- Démarrer Fawkes avec des arguments qu'il ne connaît pas encore.

## 4. Anti-objectifs (échec même si « ça marche »)

- Un jeton visible, journalisé, écrit dans un fichier ou dans un message d'erreur.
- Une demande envoyée à Fawkes, ou Fawkes démarré, sans clic de l'utilisateur.
- Une entrée, un choix ou un réglage perdu par une mise à jour, deux instances ou un fichier abîmé.
- Une avalanche de notifications au premier chargement d'un compte.
- Une erreur d'un compte qui efface les entrées des autres, ou les siennes en cache.

## 5. Contraintes

- Rust edition 2024, eframe/egui 0.37 en rendu glow, une crate bibliothèque + exécutable.
- Interface en français ; raccourcis réglables ; thèmes système / sombre / clair.
- Aucune donnée réelle dans les tests (contoso, fabrikam, northwind), aucun jeton de
  l'environnement, aucune organisation réelle ; réseau seulement par un transport factice en test.
- `cargo fmt`, `cargo clippy --all-targets -- -D warnings` et `cargo test` verts à chaque commit ;
  un commit par étape, message en français, identité git du dépôt, rien de poussé.
- Ne modifier aucun autre dépôt : les besoins vis-à-vis de Fawkes et DragonTree vont dans
  `docs/contrat-local.md`.

## 6. Décisions de conception

### 6.1 Comptes

- `Account { id, forge, host, orgs, auth: Token | Gh, username, display_name }` dans les réglages ;
  le jeton dans le coffre (service « Owlery », utilisateur `account:<id>`).
- Sans compte GitHub configuré, si `gh` est installé, un compte implicite « GitHub (gh) » est lu
  (l'ordre du premier jet reste : jeton, sinon gh, sinon écran d'accueil).
- Le jeton du premier jet (`github:token`) est repris dans un compte au démarrage, puis l'ancienne
  entrée du coffre est supprimée (seulement après l'écriture de la nouvelle).
- Retirer un compte supprime son jeton et ses entrées en cache ; ses choix (lu, terminé) suivent la
  règle des 30 jours.
- Les entrées portent leur compte : une lecture ne remplace que les entrées du compte lu. Les
  entrées du premier jet (sans compte) sont rattachées au premier compte GitHub lu.
- Identifiant d'entrée : inchangé pour l'hôte par défaut de la forge (`GitHub:contoso/api#1:Mention`),
  l'hôte ajouté sinon (`GitHub@ghe.contoso.test:…`) : les choix du premier jet restent valables.

### 6.2 Lecture

- Une lecture par compte, chacune dans son fil ; erreur et quota par compte. Le résumé en tête dit
  combien de comptes ont été lus et lesquels ont échoué, avec la raison.
- Doublons : une même PR ou un même ticket n'apparaît qu'une fois par compte, avec le type le plus
  utile : Revue demandée, CI en échec, Ma PR, Ticket assigné, Mention.
- GitLab : MR où je suis relecteur, mes MR (pipeline de tête), à-faire « mentionné » ou « cité
  directement », tickets assignés. Jeton : `read_api`.
- Azure DevOps : par organisation, PR où je suis relecteur, mes PR (dernière build de la PR), éléments
  de travail assignés et mentions récentes (`@RecentMentions`). Jeton : Code, Work Items et Build en
  lecture. Services (dev.azure.com) en API 7.1, Server en 5.0, comme DragonTree.

### 6.3 Notifications

- Après une lecture : les entrées devenues non lues (nouvelles, ou revenues par une activité), des
  types cochés (par défaut : revue, CI, mention, ticket ; pas « Ma PR »). Rien au premier
  chargement d'un compte. Une seule bulle qui résume (« 3 nouvelles entrées » et les titres).
- Report arrivé à échéance : l'entrée redevient non lue et une bulle « Rappel » s'affiche.
- Pas de bulle quand la fenêtre d'Owlery a le focus. Un clic sur la bulle ramène Owlery.

### 6.4 Contrat local

Aligné sur les propositions de Menagerie, Patronus et Grimoire : canal `\\.\pipe\<application>-<SID>`
réservé au compte, une ligne JSON par message, `"v": 1`, champ `demande`, réponse `ok` / `erreur`.
Détail et demandes : `docs/contrat-local.md`.

- Owlery reçoit `afficher` (`type` facultatif), `actualiser`, `etat` (`depot_url` facultatif).
- Deuxième lancement d'Owlery (même dossier d'état) : il envoie `afficher` et se termine.
- *Corriger avec Claude* envoie à Fawkes `ouvrir` (`dir`, `titre`, `claude`, `worktree`,
  `consigne` collée sans être envoyée). Fawkes sans canal : dialogue *Démarrer Fawkes* (lancé sans
  argument, puis attente du canal 20 s au plus), *Copier le contexte*, *Annuler*.

### 6.5 Dépôts locaux

Dossiers racines dans les réglages, parcourus en arrière-plan (profondeur 3) ; un dépôt est reconnu
par ses `remote` (https, ssh, formes Azure). Le dossier choisi à la main l'emporte toujours.

## 7. Laissé à l'exécutant

Mise en page fine des dialogues, textes d'aide, organisation interne des modules d'interface, choix
des fixtures, tant que les tests des tâches passent et que les contraintes tiennent.
